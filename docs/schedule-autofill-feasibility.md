# スケジュール自動入力 — 技術検討

## 結論

実現可能。新規イベント画面の先頭に「URLまたは画像から自動入力」カードを追加し、認証済みの解析APIを経由して既存フォームへ候補値を反映する。

解析結果は自動保存せず、各項目をユーザーが確認・修正してから既存の「保存」を押す方式を推奨する。サイトごとの表記揺れ、画像の解像度、複数公演を含むページなどにより、100%の正確性は保証できないため。

## 推奨フロー

1. ユーザーがURLを貼る、または画像を1枚選ぶ。
2. フロントエンドが `POST /schedule-import/preview` を呼ぶ。
3. バックエンドがURL本文の取得、または画像データの検証を行う。
4. AIへ構造化JSONでの抽出を依頼し、日付・時刻・文字数・許容項目をサーバー側でも検証する。
5. フロントエンドが候補値と注意事項を表示する。
6. ユーザーが「フォームに反映」を押し、既存フォームを確認・修正して保存する。

APIレスポンスの例:

```json
{
  "title": "TenTwenty LIVE 2026「Velvet Dinner」",
  "date": "2026-10-20",
  "open": "17:30",
  "start": "18:30",
  "end": null,
  "area": "東京",
  "venue": "SGC HALL ARIAKE",
  "warnings": ["終演時刻は見つかりませんでした"],
  "source_type": "image"
}
```

## 影響範囲

| 対象 | 主な変更 | 規模 |
| --- | --- | --- |
| `frontend/app/new.tsx` | 取込カード、解析中・エラー・候補確認状態、既存stateへの反映 | 中 |
| フロントエンド共通部品 | URL入力、画像プレビュー、候補確認を独立コンポーネント化 | 中 |
| `expo-image-picker` / `app.json` | 既存依存を再利用。写真権限の説明をイベント画像にも合う文言へ変更 | 小 |
| `backend/src/main.rs` | 認証付きpreview API、URL取得、AI構造化抽出、検証、レート制限 | 中〜大 |
| 環境変数・デプロイ | 既存の `ANTHROPIC_API_KEY` を再利用可能。タイムアウト・サイズ上限を設定 | 小 |
| DB | MVPでは変更不要。解析結果を保存しない | なし |
| テスト | URL取得、画像、表記揺れ、欠損、複数公演、巨大画像、危険URLのケース | 中 |

## 実装時の重要事項

- URL取得はSSRF対策が必須。`http/https` のみ許可し、localhost、プライベートIP、メタデータIP、過剰なリダイレクトを拒否する。
- HTMLと画像にはサイズ上限を設ける。例: HTML 2 MB、画像 5 MB。画像は送信前にリサイズ・圧縮する。
- URLの内容は命令ではなく未信頼データとして扱う。AIへの指示と抽出対象本文を明確に分離する。
- AI応答はJSON Schemaに固定し、`YYYY-MM-DD` / `HH:MM`、文字数、列挙値をバックエンドで再検証する。
- エリアはユーザーの既存選択肢と正規化照合する。「東京都→東京」などは変換し、一致しない場合は勝手に選択肢を増やさず警告する。
- 複数公演が見つかった場合は1件に決め打ちせず、公演選択を返す。MVPで未対応なら「複数公演のページは対象外」と明示する。
- 認証、ユーザー単位のレート制限、短いタイムアウト、利用量ログを設け、外部API費用の濫用を防ぐ。
- 元画像はMVPでは保存しない。解析完了後に破棄すると、個人情報・著作物の保持リスクを抑えられる。

## 段階的な進め方

### MVP

- URL 1件または画像 1枚
- 1公演のみ
- タイトル、日付、開場、開演、終演、エリア、会場を抽出
- 候補確認後にフォームへ反映
- DB変更なし

### 次段階

- 複数公演の一括候補と選択
- 出演者、チケット代、販売元、備考の抽出
- 対応サイト別の決定論的パーサーを追加し、AI呼び出し回数と費用を削減
- ユーザー訂正結果を品質評価に利用（明示的な同意と保持方針が必要）
